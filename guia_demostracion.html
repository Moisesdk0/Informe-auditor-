Módulo 1 — Autenticación

HAL-001 · HAL-002

HAL-001

Sin Regeneración de Sesión (Session Fixation)

Medio

El identificador de la sesión no cambia al iniciar sesión: alguien que ya tenía ese identificador puede seguir usándolo después de que inicies sesión como administrador.

Impacto: si un atacante le hace llegar a la víctima un enlace con un ID de sesión que él ya conoce (por ejemplo, con un parámetro manipulado), y la víctima inicia sesión con ese ID, el atacante puede reutilizarlo después y quedar autenticado con sus mismos privilegios — incluidos los de administrador — sin necesitar su contraseña.
  1. Abre index.php y presiona F12 → pestaña Application → Cookies. Anota el valor de PHPSESSID.
  2. Inicia sesión con el usuario admin (resolviendo el reCAPTCHA).
  3. Vuelve a Application → Cookies: el valor de PHPSESSID es exactamente el mismo.
Señala las dos capturas lado a lado: el mismo valor de cookie antes y después del login.
HAL-002

Error Lógico en Verificación de Rol

Medio

La condición !$seccion == true en head.php es ambigua por cómo PHP evalúa los operadores: funciona por casualidad, no porque esté bien escrita.

Impacto: hoy el resultado práctico es correcto, pero el código es engañoso. Si alguien lo "simplifica" pensando que entiende la lógica, podría dejar sin querer una ruta de acceso para usuarios sin permiso de administrador, y nadie lo notaría hasta que ya estuviera explotado.
  1. No se demuestra con el sistema en ejecución — es un hallazgo de lectura de código.
  2. Abre head.php:12 en el editor.
  3. Explica: PHP evalúa primero !$seccion y después compara ese resultado con true, no lo que el nombre de la variable sugiere a simple vista.
head.php — línea 12
// condición ambigua por precedencia de operadores if(!$seccion == true || $rol != 1) { header("location: destroyer.php"); // ← FALTA exit(); — ejecución puede continuar tras la redirección }
Muestra la línea original y, al lado, la versión corregida con comparación explícita (!== true) y exit().

Módulo 2 — Recuperación de Contraseña

HAL-003 · HAL-004 · HAL-005

HAL-003

Credenciales de Correo Expuestas en el Código

Crítico

La contraseña de la cuenta de Gmail que envía los correos de recuperación está escrita directamente dentro del código.

Impacto: quien consiga acceso al código (servidor, un backup, o un repositorio mal configurado) controla la cuenta de correo corporativa completa: puede enviar phishing o spam a nombre de la empresa, leer el historial de mensajes, y no se puede revocar esa contraseña sola sin desactivar la verificación en dos pasos de toda la cuenta.
  1. Abre enviar_token.php, alrededor de la línea 37.
  2. Señala la línea con el usuario y la contraseña de Gmail en texto plano.
enviar_token.php — líneas 37-38
$mail->Username = 'uptag2026@gmail.com'; // ← cuenta expuesta $mail->Password = 'xwnlhyllvdpdamyn'; // ← App Password de Gmail expuesta
No ejecutes ni muestres el envío real de correo con estas credenciales en una demo pública: esa contraseña de aplicación debería estar ya revocada. Basta con mostrar el código fuente.
HAL-004

Depuración SMTP Visible en Producción

Crítico

Al pedir recuperar la contraseña, el sistema muestra en pantalla toda la conversación técnica con el servidor de Gmail — información que solo debería ver un programador, no el usuario.

Impacto: expone el usuario de correo codificado en base64 (fácil de decodificar) a cualquier visitante del sitio, sin necesidad de iniciar sesión. Facilita que alguien reconstruya parte de las credenciales de HAL-003 o entienda cómo está armado el servidor de correo.
  1. En index.php, pulsa ¿Olvidó su contraseña? → RECUPERAR.
  2. Escribe un correo que exista en la base de datos y envía el formulario.
  3. En la respuesta, señala el bloque de texto con líneas como SMTP -> FROM SERVER y 250 OK.
enviar_token.php — línea 41
$mail->SMTPDebug = 3; // ← vuelca la sesión SMTP completa al HTML
Resalta que ese texto técnico lo ve cualquier visitante, autenticado o no.
HAL-005

Sin Límite de Intentos en Recuperación

Medio

Se puede pedir el correo de recuperación cuantas veces se quiera, sin ningún bloqueo.

Impacto: un atacante puede automatizar miles de solicitudes para saturar la bandeja de entrada de un usuario, abusar del servicio de correo de la empresa (riesgo de que Gmail bloquee la cuenta por spam), o usar las respuestas distintas del sistema para averiguar qué correos existen registrados.
  1. Envía el formulario de recuperación 4 o 5 veces seguidas, con el mismo correo.
  2. Muestra que el sistema responde igual cada vez, sin bloquear ni pedir un captcha adicional.

Módulo 3 — Gestión de Usuarios

HAL-006 · HAL-007 · HAL-008

HAL-006

Construcción Insegura de SQL en Registro

MedioNo explotable

El código arma la consulta SQL pegando directamente lo que escribe el usuario, en vez de usar una consulta preparada. En esta versión de PHP no se puede aprovechar, pero sigue siendo una mala práctica.

Impacto: hoy la protección es incidental (un efecto colateral de htmlspecialchars()), no intencional. Si el proyecto se ejecuta en una versión de PHP anterior a 8.1, si alguien cambia esa función de sanitización, o si estas mismas variables se reutilizan en otra consulta, el mismo código permitiría inyección SQL real — lectura o alteración de toda la base de datos.
  1. Ve a Agregar usuario, campo correo, escribe: ' OR '1'='1' --
  2. Completa el resto del formulario y envíalo.
  3. Muestra que no pasa nada raro: la consulta queda bien formada y 0 filas, sin ningún error.
  4. Abre add_user.php:29 y explica por qué: htmlspecialchars() con ENT_QUOTES (por defecto desde PHP 8.1) neutraliza la comilla.
add_user.php — línea 29: sanitización HTML usada en contexto SQL
$email = htmlspecialchars($_POST['email']); $user = htmlspecialchars($_POST['user']); $check = mysqli_query($conn, "SELECT * FROM user WHERE name = '$user' OR gmail = '$email'" ); // payload ' OR '1'='1' -- se convierte en ' OR '1'='1' -- // resultado real: sin error de SQL, 0 filas → no explotable en PHP 8.1+
Aclara al público que esto demuestra la mala práctica en el código, no un ataque exitoso — ya se probó también con sqlmap (ver HAL-006/HAL-009 en inyecciones.md) y ningún parámetro resultó inyectable.
HAL-007

Operaciones Destructivas vía GET

Alto

Se puede borrar un usuario o un material solo con visitar una dirección web — sin ningún botón de confirmación.

Impacto: un enlace, una imagen oculta en un correo, o un anuncio malicioso en otra página puede disparar esta misma URL mientras el administrador tiene la sesión abierta — sin que haga clic en nada dentro de BuildSafe. El resultado es pérdida de datos irreversible y sin rastro de quién lo causó.
  1. Inicia sesión como admin.
  2. Crea de antemano un usuario de prueba desechable para esta demo (no uses uno real).
  3. En la barra de direcciones, visita: list_user.php?delete_id=<id_de_prueba>
  4. Muestra que el usuario desaparece de la lista al instante, sin cuadro de confirmación.
Enfatiza que un simple enlace o imagen en otra página podría disparar esta misma URL.
HAL-008

Sin Protección CSRF

Alto

Un sitio externo puede enviar, sin que tú lo notes, un formulario que crea un usuario en BuildSafe — aprovechando que tu sesión de administrador ya está abierta.

Impacto: no solo crear usuarios — cualquier formulario del sistema (editar materiales, cambiar estados) es vulnerable al mismo patrón. Basta con que el administrador visite una página cualquiera mientras tiene la sesión abierta para que ocurra la acción, sin que lo vea ni lo apruebe.
  1. Prepara, fuera del proyecto, un archivo HTML con un formulario oculto que apunte a add_user.php con los mismos campos.
  2. Con la sesión de admin abierta en el navegador, abre ese archivo HTML en otra pestaña y pulsa el botón de envío.
  3. Vuelve a BuildSafe y muestra que el usuario se creó, aunque el formulario vivía en otra página.
Si no tienes ese archivo de prueba preparado, dilo y lo armamos antes de la demo.

Módulo 4 — Materiales y Movimientos

HAL-009

HAL-009

Consultas SQL sin Prepared Statements

Alto

Varias consultas arman el texto SQL pegando directamente valores, en vez de usar parámetros preparados — el mismo problema de fondo que HAL-006, pero en otros archivos.

Impacto: hoy los valores pasan por intval(), pero el INSERT de la bitácora interpola una cadena de texto directamente, el caso más riesgoso. Basta un cambio futuro que agregue un campo de texto sin pasar por ese mismo cuidado para introducir una inyección SQL real.
  1. Es un hallazgo de código: abre list_user.php:52,65.
  2. Ábrelo junto a list_materials.php, que sí usa $conn->prepare(), para contrastar el antes/después dentro del mismo proyecto.
list_user.php — líneas 52, 65: interpolación directa
mysqli_query($conn, "UPDATE user SET active = $new_status WHERE user_id = $user_id" ); mysqli_query($conn, "DELETE FROM user WHERE user_id = $id" ); // list_material.php — líneas 34, 40, 47: mismo patrón

Módulo 5 — Inspección del Código Fuente

HAL-010 a HAL-017

HAL-010

Archivos Sensibles en el Webroot

Alto

El volcado completo de la base de datos quedó dentro de la carpeta pública del sitio web.

Impacto: cualquier persona en internet, sin necesitar cuenta ni contraseña, puede descargar todos los usuarios, contraseñas hasheadas (y la de HAL-012, en texto plano), materiales y movimientos de inventario con una sola dirección web.
  1. En el navegador, visita directamente: http://localhost/buildsafe_system1/test2.sql
  2. Muestra que se descarga (o se muestra) el archivo completo, con usuarios, contraseñas hasheadas y toda la estructura de tablas.
HAL-011

Errores de Base de Datos Expuestos

Medio

Cuando una consulta falla, el sistema le muestra al usuario normal el mensaje técnico completo de MySQL.

Impacto: revela nombres de tablas, columnas y detalles del motor de base de datos — información que un atacante usa para planear ataques más precisos contra el sistema, aunque por sí sola no permite acceder a datos.
  1. En Agregar usuario, intenta registrar un correo que ya exista en la base de datos.
  2. Señala el mensaje Error: ... con el texto crudo que viene de $conn->error.
add_user.php:56 · list_user.php:35,71 · edit_user.php:65
// VULNERABLE — expone estructura interna: $_SESSION['message'] = "Error: " . $conn->error;
HAL-012

Contraseña sin Hash en la Base de Datos

Medio

Un usuario de la base de datos tiene la contraseña guardada tal cual, sin cifrar.

Impacto: si la base de datos se filtra o se accede a ella (como ya demuestra HAL-010), esa contraseña queda lista para usarse de inmediato, sin que el atacante necesite descifrar nada — a diferencia de las demás, protegidas con hash bcrypt.
  1. Abre phpMyAdmin → base test2 → tabla user.
  2. Busca user_id = 9 (correo ds@gmail.com) y señala la columna password: dice 123456, en texto plano.
  3. Compáralo con otra fila cualquiera, donde la contraseña es un hash bcrypt largo ($2y$10$...).
test2.sql — tabla user, user_id=9
user_id=9, gmail='ds@gmail.com', password='123456' // ← texto plano, sin hash // cualquier otra fila: password='$2y$...' (hash bcrypt real) — compara en pantalla
HAL-013

Ausencia de Control de Versiones

Medio

El proyecto no traía ningún historial de cambios (sin Git) cuando se entregó para auditar.

Impacto: sin historial, no se puede saber quién introdujo un cambio problemático ni revertirlo con confianza; si en el futuro se usa Git sin cuidado, credenciales que se "eliminen" del código fuente podrían quedar igualmente accesibles en versiones anteriores del repositorio.
  1. Muestra que la carpeta original del sistema no tenía una carpeta .git.
  2. Contrasta con esta misma carpeta de auditoría, donde sí creamos un repositorio para llevar el control del propio trabajo de auditoría.
HAL-014

Clave Secreta de reCAPTCHA Hardcodeada

Bajo

La clave secreta de reCAPTCHA está escrita directamente en el código, en vez de guardarse por fuera.

Impacto: si esta clave se filtra, alguien puede falsificar verificaciones de reCAPTCHA desde cualquier servidor, anulando la protección contra bots en el login y debilitando esa barrera frente a ataques automatizados (como HAL-005 y los intentos de fuerza bruta).
  1. Abre index.php:47 y señala la línea con la clave.
index.php — línea 47
$secretkey = '6LdVkrIrAAAAALXGfzMhYeIlaTLb1wDkX8NgHTVI';
HAL-015

Sin Cabeceras de Seguridad HTTP

Bajo

El servidor no envía las cabeceras que ayudan a protegerse de clickjacking o de que el navegador adivine mal el tipo de archivo.

Impacto: sin X-Frame-Options, el sitio puede incrustarse dentro de otra página invisible para engañar a un usuario a hacer clic en algo distinto de lo que ve (clickjacking); sin X-Content-Type-Options, versiones antiguas de navegadores pueden interpretar mal un archivo y ejecutarlo como si fuera otro tipo.
  1. F12 → pestaña Network, recarga cualquier página.
  2. Abre la petición principal → pestaña Headers → Response Headers.
  3. Señala que faltan X-Frame-Options, X-Content-Type-Options, etc.
head.php — cabeceras que faltan agregar al inicio
// ninguna de estas líneas existe hoy en head.php: header("X-Frame-Options: DENY"); header("X-Content-Type-Options: nosniff"); header("Referrer-Policy: strict-origin-when-cross-origin");
HAL-016

Falta Verificación de Rol al Cambiar Estado

Alto

Se puede desactivar a otro administrador: la validación que sí existe para "eliminar" nunca se copió al botón de "activar/desactivar".

Impacto: cualquier administrador autenticado (incluso una cuenta comprometida con pocos privilegios reales) puede desactivar a todos los demás administradores, incluido el principal, dejando el sistema efectivamente sin control administrativo.
  1. Ten listo un segundo usuario con rol administrador, creado para la demo.
  2. Visita: list_user.php?toggle_status=<id_del_otro_admin>
  3. Muestra que su cuenta queda desactivada — aunque la interfaz normalmente oculta ese botón para filas de administrador.
list_user.php — línea 16-19 (DELETE sí valida) vs. línea 46-58 (toggle_status no)
// el DELETE sí valida el rol del objetivo: if($row['rol'] == 1){ $_SESSION['message'] = "No se puede eliminar otro administrador"; } // toggle_status NO repite esa validación: if(isset($_GET['toggle_status'])) { $user_id = intval($_GET['toggle_status']); if($id != $user_id){ // ← solo compara contra uno mismo, no valida $row['rol'] mysqli_query($conn, "UPDATE user SET active = $new_status WHERE user_id = $user_id"); } }
HAL-017

Ausencia de Documentación Técnica

Bajo

El proyecto no traía ningún README ni guía de instalación.

Impacto: no es un vector de ataque por sí mismo, pero sin un estándar documentado de dónde deben ir las credenciales, cada desarrollador resuelve ese problema a su manera — y la opción más simple termina siendo escribirlas directo en el código, como ya pasó en HAL-003 y HAL-014.
  1. Muestra la carpeta raíz del proyecto original y señala que no hay README.md, .env.example ni carpeta docs/.

Módulo 6 — Herramientas Automatizadas

HAL-018 a HAL-027 · OWASP ZAP · Lighthouse

HAL-018

Listado de Directorios Habilitado

MedioOWASP ZAP

Apache muestra la lista de archivos de una carpeta en vez de dar un error, cuando esa carpeta no tiene un index.php.

Impacto: expone la estructura completa de archivos de carpetas como /src/, que puede contener código fuente. Un atacante usa ese listado para encontrar exactamente qué archivos atacar, en vez de tener que adivinarlos.
  1. En el navegador, visita: http://localhost/buildsafe_system1/src/
  2. Muestra el listado "Index of /buildsafe_system1/src" con los archivos dentro.
HAL-019

Divulgación de Rutas Internas por Warnings de PHP

MedioOWASP ZAP

El servidor tiene activados los avisos de error de PHP, y esos avisos revelan la ruta completa del servidor.

Impacto: la ruta absoluta (C:\xampp\htdocs\buildsafe_system1\) confirma a un atacante el sistema operativo, el servidor y la estructura exacta de carpetas, información útil para apuntar otros ataques específicos a esa instalación.
  1. Ten lista la captura ya tomada: el warning Undefined array key "id" in C:\xampp\htdocs\buildsafe_system1\head.php on line 5.
  2. Es más estable mostrarlo como evidencia guardada que intentar reproducirlo en vivo, porque depende del estado exacto de la sesión.
Evidencia capturada por OWASP ZAP (head.php:5, list_user.php:79)

Evidencia de respaldo recomendada para este hallazgo: captura de pantalla ya guardada, en vez de reproducción en vivo.
HAL-020

Scripts de Terceros sin Atributo de Integridad

MedioOWASP ZAP

El sistema carga librerías desde internet (CDN) sin una "huella digital" que confirme que el archivo no fue alterado.

Impacto: si el CDN externo es comprometido, el código malicioso se ejecutaría directamente en el navegador de cualquier usuario del sistema — administradores incluidos — sin que BuildSafe tenga forma de detectarlo o bloquearlo.
  1. Ctrl+U (ver código fuente) en index.php.
  2. Busca las etiquetas <script src="https://cdn.jsdelivr.net/..."> y señala que no tienen el atributo integrity.
index.php — etiquetas tal como están hoy
<script src="https://cdn.jsdelivr.net/npm/sweetalert2@11"></script> <script src="https://www.google.com/recaptcha/api.js" async defer></script> // ← ninguna de las dos tiene el atributo integrity="sha384-..."
HAL-021

Cookie de Sesión sin HttpOnly ni SameSite

BajoOWASP ZAP

La cookie de sesión no tiene dos protecciones estándar: que JavaScript no pueda leerla, y que no se envíe a otros sitios.

Impacto: sin HttpOnly, si llegara a existir un XSS en el sistema, un atacante podría robar la cookie de sesión con JavaScript; sin SameSite, la cookie también se envía en peticiones hacia otros sitios, agravando directamente el ataque CSRF de HAL-008.
  1. F12 → Application → Cookies → fila PHPSESSID.
  2. Señala que las columnas HttpOnly y SameSite aparecen vacías.
Cabecera real enviada por el servidor
Set-Cookie: PHPSESSID=k3il9s5itfj1t8s7di3mgnriq8; path=/ // ← sin HttpOnly, sin SameSite, sin Secure
HAL-022

Fuga de Versiones en Cabeceras HTTP

BajoOWASP ZAP

El servidor anuncia, en cada respuesta, la versión exacta de Apache y de PHP que usa.

Impacto: un atacante sabe exactamente qué versión de Apache y PHP buscar en bases de datos de vulnerabilidades conocidas, ahorrándose el trabajo de adivinar y pudiendo apuntar directo a fallas ya documentadas de esa versión específica.
  1. F12 → Network → cualquier petición → Response Headers.
  2. Señala Server: Apache/2.4.58 ... PHP/8.2.12 y X-Powered-By: PHP/8.2.12.
Cabeceras reales de respuesta
Server: Apache/2.4.58 (Win64) OpenSSL/3.1.3 PHP/8.2.12 X-Powered-By: PHP/8.2.12
HAL-023

Redirecciones con Cuerpo de Respuesta (Hipótesis)

BajoOWASP ZAP

Cuando el sistema redirige al login, de todos modos envía algo de contenido — un indicio, no confirmado, de que falta cortar la ejecución justo después de redirigir.

Impacto: es una hipótesis, no confirmada todavía. Si en efecto falta un exit() tras header('Location: ...'), el código que sigue podría seguir ejecutándose aunque el usuario ya fue redirigido — algo del mismo tipo que el problema ya confirmado en HAL-002.
  1. Abre ZAP → pestaña Historial.
  2. Busca una petición con código 302 hacia destroyer.php y ábrela.
  3. En la Respuesta, señala que el cuerpo no está vacío (636 bytes).
Ejemplo real registrado por ZAP (dashboard.php)
HTTP/1.1 302 Found Location: destroyer.php // tamaño del cuerpo de la respuesta: 636 bytes (no debería tener cuerpo)
Requiere tener ZAP abierto con ese historial ya capturado de una sesión anterior.

HAL-027

Peso de Página y Rendimiento en Móvil

BajoLighthouse

Las páginas cargan demasiadas librerías completas desde internet, lo que las hace lentas en una conexión móvil simulada.

Resumen Ejecutivo

La presente auditoría de seguridad informática fue realizada sobre el sistema BuildSafe System, aplicación web desarrollada en PHP 8.2 para la gestión de inventario de materiales de la empresa CONFALVI C.A. El análisis fue ejecutado mediante revisión estática del código fuente, aplicando como marco de referencia el estándar OWASP Top 10 — 2025 (publicado en enero de 2026, la revisión vigente al momento de esta auditoría), complementada con pruebas dinámicas automatizadas mediante OWASP ZAP 2.17.0 y Lighthouse 13.5.0 (sección 8). Se analizaron un total de 27 archivos PHP que conforman el núcleo funcional del sistema, identificando vulnerabilidades distribuidas en los módulos de autenticación, recuperación de contraseña, gestión de usuarios, gestión de materiales, configuración del servidor y pruebas con herramientas automatizadas.

Como resultado del análisis, se encontraron 27 hallazgos de seguridad, de los cuales 2 son de severidad Crítica, 5 de severidad Alta, 10 de severidad Media y 10 de severidad Baja. El nivel de riesgo global del sistema fue evaluado en 7.0 / 10 — ALTO, determinado por la gravedad de los hallazgos críticos y altos de la revisión de código; los 10 hallazgos adicionales detectados con herramientas automatizadas (sección 8) son de severidad Media y Baja y no modifican esa calificación. El resultado indica que el sistema no debe ser expuesto a producción pública en su estado actual sin corregir al menos los hallazgos críticos y altos.

Sin Regeneración de ID de Sesión Tras Autenticación
Identificación
HAL-001
Riesgo
Medio
Estatus
Nuevo
Descripción

Tras una autenticación exitosa en index.php, el sistema no invoca session_regenerate_id(true). Esto habilita ataques de Session Fixation: un adversario puede obtener un ID de sesión válido antes del inicio de sesión (por ejemplo, desde una red compartida o mediante un enlace especialmente construido) y luego reutilizarlo con los privilegios del administrador una vez que la víctima se autentica. OWASP clasifica este tipo de falla bajo A07 — Fallas de Autenticación.

// index.php — línea 88-116: tras password_verify() no se regenera sesión // El ID de sesión anterior sigue siendo válido con nuevos privilegios if(password_verify($password, $user_data['password'])) { // ← FALTA: session_regenerate_id(true); $_SESSION['user'] = $user_data['name']; $_SESSION['id'] = $user_data['user_id']; $_SESSION['seccion'] = true; // sesión fijada sin cambiar ID header("Location: menu.php"); }
Recomendación
Corrección — agregar inmediatamente después de verificar la contraseña
if(password_verify($password, $user_data['password'])) { session_regenerate_id(true); // ← Nuevo ID, invalida el anterior $_SESSION['user'] = $user_data['name']; $_SESSION['id'] = $user_data['user_id']; $_SESSION['seccion'] = true; header("Location: menu.php"); }
Ubicación:index.php — líneas 88-116 (bloque de autenticación exitosa)

Error Lógico en la Verificación de Autorización de Rol
Identificación
HAL-002
Riesgo
Medio
Estatus
Nuevo
Descripción

El archivo head.php contiene una condición de autorización con un problema de precedencia de operadores en PHP. La expresión !$seccion == true se evalúa como (!$seccion) == true (equivalente a $seccion == false) en lugar del intuitivo !($seccion == true). Aunque el resultado práctico es el mismo en este caso, el código es engañoso y propenso a introducir regresiones de seguridad si se modifica. Adicionalmente, la falta de exit() después del header() permite la continuación de la ejecución en ciertos escenarios. OWASP: A07 — Fallas de Autenticación.

// head.php — línea 12: condición ambigua por precedencia de operadores if(!$seccion == true || $rol != 1) { header("location: destroyer.php"); // ← FALTA exit(); — ejecución puede continuar tras la redirección }
Recomendación
Reescribir con comparación explícita y agregar exit()
if ($seccion !== true || $rol !== 1) { header("Location: destroyer.php"); exit(); // Detener ejecución inmediatamente }
Ubicación:head.php — línea 12 (guard de autorización de páginas admin)

Identificación
HAL-003
Riesgo
Crítico
Estatus

Descripción

El archivo enviar_token.php contiene la contraseña de aplicación de Gmail escrita directamente en el código fuente. Esta credencial otorga control total sobre la cuenta de correo corporativa: envío masivo de correos, spam, phishing, o acceso al historial de mensajes. Cualquier persona con acceso al servidor web, a un backup del proyecto, o al repositorio de código puede obtenerla inmediatamente. Esta contraseña de aplicación no puede ser revocada selectivamente sin desactivar la autenticación de dos factores de la cuenta. OWASP: A07 — Fallas de Autenticación.

// enviar_token.php — líneas 37-38 $mail->Username = 'uptag2026@gmail.com'; // ← Cuenta expuesta $mail->Password = 'xwnlhyllvdpdamyn'; // ← App Password Gmail expuesta // Accesible en: C:\xampp\htdocs\buildsafe_system1\enviar_token.php
Recomendación
Mover credenciales a variables de entorno — revocar la contraseña expuesta inmediatamente
// 1. Crear archivo .env FUERA del webroot (nunca en htdocs) MAIL_USER=uptag2026@gmail.com MAIL_PASS=nueva_app_password_generada // 2. En enviar_token.php $mail->Username = getenv('MAIL_USER'); $mail->Password = getenv('MAIL_PASS');

Modo Debug SMTP Nivel 3 Activo en Producción
Identificación
HAL-004
Riesgo
Crítico
Estatus
Nuevo
Descripción

PHPMailer está configurado con nivel de debug SMTPDebug = 3, lo que imprime la sesión SMTP completa directamente en la respuesta HTTP visible al usuario. Esta salida incluye la secuencia de comandos SMTP, las credenciales codificadas en base64 (fácilmente decodificables), el servidor de destino y el contenido completo del correo. Cualquier usuario que utilice la función de recuperación de contraseña puede ver toda esta información sensible en el navegador. OWASP: A09 — Fallas en el Registro y Alertas de Seguridad.

// enviar_token.php — línea 41 $mail->SMTPDebug = 3; // ← Vuelca sesión completa al HTML // Salida visible en el navegador del usuario: // 2026-06-15 14:32:11 CLIENT -> SERVER: AUTH LOGIN // 2026-06-15 14:32:11 CLIENT -> SERVER: dXB0YWcyMDI2QGdtYWlsLmNvbQ== // 2026-06-15 14:32:11 CLIENT -> SERVER: eHdubGh5bGx2ZHBkYW15bg== // (decodificado: uptag2026@gmail.com / xwnlhyllvdpdamyn)
Recomendación
Deshabilitar completamente en producción
$mail->SMTPDebug = 0; // 0 = Sin salida de debug // Para depuración local usar: $mail->SMTPDebug = 2; // Y redirigir a archivo de log, nunca a HTML

El endpoint enviar_token.php no implementa ninguna restricción de frecuencia (rate limiting). Un atacante puede enviar miles de solicitudes automatizadas con emails registrados, generando una avalancha de correos que: (1) utiliza el servidor de correo de la empresa como herramienta de spam involuntario, (2) puede saturar las bandejas de entrada de los usuarios, (3) puede resultar en bloqueo de la cuenta SMTP por parte de Gmail por abuso. // enviar_token.php — no existe ninguna restricción de tiempo // Un atacante puede ejecutar esto 1000 veces en segundos: for($i = 0; $i < 1000; $i++) { // POST /enviar_token.php email=victima@empresa.com // Cada request genera y envía un token sin validación }

Construcción Insegura de Consulta SQL en Verificación de Duplicados
Identificación
HAL-006
Riesgo
Medio
Estatus
Nuevo
Descripción

En add_user.php, los valores de $user y $email se interpolan directamente dentro de una consulta SQL sin sentencias preparadas, pasando únicamente por htmlspecialchars() — una función de sanitización para contexto HTML, no para contexto SQL. Se verificó en vivo contra la instalación real (PHP 8.2.12) el payload clásico ' OR '1'='1' --: desde PHP 8.1, htmlspecialchars() aplica ENT_QUOTES por defecto, por lo que la comilla simple se convierte en la entidad literal &#039; antes de llegar a la consulta. La prueba directa contra la base de datos confirmó que la consulta se ejecuta sin error y retorna 0 filas — el bypass de la lógica de duplicados no se logra en esta versión de PHP. Aun así, el hallazgo se mantiene porque la protección es incidental, no intencional: no existe ninguna sentencia preparada ni escape orientado a SQL, por lo que el código queda expuesto si el proyecto se ejecuta bajo PHP < 8.1, si algún desarrollador cambia la función de sanitización, o si estas mismas variables se reutilizan en otra consulta sin pasar de nuevo por htmlspecialchars(). OWASP: A05 — Inyección (patrón de diseño, no explotación confirmada).

Evidencia — Prueba en Vivo Ejecutada Contra la Base de Datos Real
Captura de consola de la prueba ejecutada el 15-jul-2026 contra test2 (PHP 8.2.12): se reprodujo exactamente la línea vulnerable de add_user.php:29 con el payload ' OR '1'='1' --. El resultado real — 0 filas devueltas, sin error de SQL — confirma que htmlspecialchars() con ENT_QUOTES (por defecto desde PHP 8.1) neutraliza el bypass antes de que la comilla llegue a la consulta.
// add_user.php — línea 29: sanitización HTML usada en contexto SQL $email = htmlspecialchars($_POST['email']); $user = htmlspecialchars($_POST['user']); $check = mysqli_query($conn, "SELECT * FROM user WHERE name = '$user' OR gmail = '$email'" ); // Prueba en vivo (PHP 8.2.12 / test2.sql) — payload: ' OR '1'='1' -- // Tras htmlspecialchars(): ' OR '1'='1' -- // Consulta final: SELECT * FROM user WHERE name='attacker' // OR gmail='' OR '1'='1' -- ' // Resultado real: sin error de SQL, 0 filas devueltas → NO explotable en PHP 8.1+
Recomendación
Usar Prepared Statements — no depender de un efecto colateral de PHP para la seguridad
$stmt = $conn->prepare( "SELECT user_id FROM user WHERE name = ? OR gmail = ?" ); $stmt->bind_param("ss", $_POST['user'], $_POST['email']); $stmt->execute(); $result = $stmt->get_result(); if ($result->num_rows > 0) { /* ya existe */ }
Ubicación:add_user.php — línea 29 (consulta de verificación de duplicados) · verificado en vivo el 15-jul-2026

Operaciones Destructivas Ejecutadas Mediante Petición GET
Identificación
HAL-007
Riesgo
Alto
Estatus
Nuevo
Descripción

Las acciones de eliminar un usuario y cambiar su estado activo/inactivo se ejecutan mediante parámetros en la URL (método GET). Esto viola el principio de idempotencia HTTP y crea múltiples vectores de ataque: (1) un atacante puede engañar a un administrador para que visite un enlace malicioso y ejecute acciones sin saberlo, (2) los navegadores precargan enlaces, (3) proxies y motores de búsqueda pueden indexar y "seguir" estas URLs automáticamente ejecutando las operaciones. El mismo patrón se repite en el módulo de materiales: list_material.php (interfaz de rol 1) y list_materials2.php (interfaz duplicada de rol 2, incluida vía head2.php) exponen ?delete_id= y ?toggle_status= sin token ni confirmación, confirmando que la falla de diseño no está aislada a un archivo sino duplicada en ambas interfaces por rol. OWASP: A01 — Control de Acceso Roto.

// list_user.php — línea 5: el DELETE ya usa prepared statement (no es inyectable), // pero se ejecuta con solo visitar la URL — sin POST, sin token, sin confirmación if(isset($_GET['delete_id'])) { $delete_id = intval($_GET['delete_id']); $delete_stmt = $conn->prepare("DELETE FROM user WHERE user_id = ?"); $delete_stmt->bind_param("i", $delete_id); $delete_stmt->execute(); // ← dispara con GET, no requiere confirmación } // list_user.php — línea 46: mismo problema en el cambio de estado if(isset($_GET['toggle_status'])) { // URL: /list_user.php?toggle_status=3 ← basta con visitar esto } // list_material.php — líneas 5 y 30: idéntico patrón, interfaz de rol 1 // list_materials2.php — línea 5: idéntico patrón, interfaz duplicada de rol 2 // URL: /list_material.php?delete_id=7 // URL: /list_material.php?toggle_status=7 // URL: /list_materials2.php?delete_id=3
Recomendación
Convertir a POST con token CSRF. Usar formularios o fetch() con método POST
// En list_user.php — verificar POST + CSRF antes de operar if ($_SERVER['REQUEST_METHOD'] === 'POST' && isset($_POST['csrf_token']) && $_POST['csrf_token'] === $_SESSION['csrf_token'] && isset($_POST['delete_id'])) { $stmt = $conn->prepare("DELETE FROM user WHERE user_id = ?"); $stmt->bind_param("i", $_POST['delete_id']); $stmt->execute(); }
Ubicación:list_user.php:5,46  ·  list_material.php:5,30  ·  list_materials2.php:5 (handlers de eliminación y toggle, duplicados en interfaz de rol 1 y rol 2)

Descripción

Ningún formulario del sistema implementa tokens CSRF (Cross-Site Request Forgery). Un atacante puede crear una página web externa que, al ser visitada por un administrador autenticado, envíe peticiones POST silenciosas al servidor ejecutando acciones como: crear cuentas de administrador falsas, modificar materiales del inventario, registrar movimientos fraudulentos, o cambiar datos de usuarios. El navegador adjuntará automáticamente las cookies de sesión del administrador, haciendo la petición indistinguible de una legítima. OWASP: A01.

// Ninguno de estos archivos valida token CSRF: // add_user.php, edit_user.php, add_material.php // register_movement.php, list_user.php // Ataque: página maliciosa con formulario oculto <form action="http://localhost/buildsafe_system1/add_user.php" method="POST"> <input name="user" value="atacante"> <input name="gmail" value="hacker@evil.com"> <input name="rol" value="1"> <!-- admin --> </form> <script>document.forms[0].submit()</script>
Recomendación
Implementar token CSRF global en head.php y validar en todos los endpoints
// head.php — generar token único por sesión if (empty($_SESSION['csrf_token'])) { $_SESSION['csrf_token'] = bin2hex(random_bytes(32)); } // En cada formulario HTML <input type="hidden" name="csrf_token" value="<?= htmlspecialchars($_SESSION['csrf_token']) ?>"> // En cada archivo que procesa POST if (!hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'] ?? '')) { die('Solicitud inválida.'); }

Consultas SQL Directas con Variables Interpoladas
Identificación
HAL-009
Riesgo
Alto
Estatus
Nuevo
Descripción

Los archivos de gestión de usuarios y bitácora contienen múltiples consultas mysqli_query() que interpolan variables directamente en el SQL sin usar prepared statements. Aunque en los casos actuales los valores son enteros validados implícitamente (intval()), el patrón establece un código inseguro por diseño que: (1) es propenso a inyección SQL cuando se modifiquen estas consultas, (2) viola el principio de defensa en profundidad, y (3) hace que las auditorías futuras sean más difíciles. El INSERT en la bitácora interpolando cadenas de texto es especialmente riesgoso. El mismo patrón se repite en list_material.php (líneas 34, 40 y 47), la interfaz de rol 1 paralela a list_materials.php/list_materials2.php, lo que confirma que la migración a prepared statements no fue aplicada de forma consistente entre los archivos que implementan la misma funcionalidad de inventario. OWASP: A05 — Inyección.

// list_user.php — líneas 52, 58, 65: interpolación directa mysqli_query($conn, "UPDATE user SET active = $new_status WHERE user_id = $user_id" ); mysqli_query($conn, "DELETE FROM user WHERE user_id = $id" ); // Bitácora — cadena de texto interpolada (más peligroso): mysqli_query($conn, "INSERT INTO binnacle (fecha_hora, id_accion, id_user) VALUES ('$time', $action, $id)" // $time es string ); // list_material.php — líneas 34, 40, 47: mismo patrón mysqli_query($conn, "SELECT estatus FROM material WHERE material_id = $material_id" ); mysqli_query($conn, "UPDATE material SET estatus = $new_status WHERE material_id = $material_id" );
Recomendación
Migrar todas las consultas a prepared statements
$stmt = $conn->prepare( "UPDATE user SET active = ? WHERE user_id = ?" ); $stmt->bind_param("ii", $new_status, $user_id); $stmt->execute(); $stmt2 = $conn->prepare( "INSERT INTO binnacle (fecha_hora, id_accion, id_user) VALUES (?, ?, ?)" ); $stmt2->bind_param("sii", $time, $action, $id); $stmt2->execute();

Falta de Verificación de Rol al Cambiar el Estado de un Usuario
Identificación
HAL-016
Riesgo
Alto
Estatus
Nuevo
Descripción

En list_user.php, el bloque que elimina un usuario sí valida el rol antes de operar: si el objetivo es administrador (rol == 1), la operación se rechaza con el mensaje "No se puede eliminar otro administrador". El bloque de toggle_status (activar/desactivar cuenta), que vive en el mismo archivo y opera sobre el mismo recurso, no repite esa validación: solo verifica que el objetivo no sea la propia sesión ($id != $user_id), pero nunca comprueba el rol del usuario afectado. La interfaz oculta el botón de "Desactivar" para las filas con rol administrador (if ($user['rol'] == 2) en la vista), pero esa es una restricción puramente visual: el endpoint en sí acepta la petición igual. Cualquier administrador autenticado puede desactivar a otro administrador — incluido el principal — visitando directamente list_user.php?toggle_status=<id>, sin ninguna confirmación adicional. Es la misma clase de falla que HAL-007 (acción sensible sin protección), pero con una causa distinta y más grave: aquí falta la comprobación de autorización en sí, no solo el método HTTP o el token CSRF — el mismo archivo demuestra que la protección correcta existe (se usó en el bloque de eliminación) pero no se replicó en el de cambio de estado. OWASP: A01 — Control de Acceso Roto.

// list_user.php — línea 16-19: el DELETE sí valida el rol del objetivo if($row['rol'] == 1){ $_SESSION['message'] = "No se puede eliminar otro administrador"; } // list_user.php — línea 46-58: toggle_status NO repite esa validación if(isset($_GET['toggle_status'])) { $user_id = intval($_GET['toggle_status']); if($id != $user_id){ // ← solo compara contra uno mismo, no valida $row['rol'] $result = mysqli_query($conn, "SELECT active FROM user WHERE user_id = $user_id"); $row = mysqli_fetch_assoc($result); $new_status = $row['active'] ? 0 : 1; mysqli_query($conn, "UPDATE user SET active = $new_status WHERE user_id = $user_id"); // ← se ejecuta igual aunque $user_id sea otro administrador } }
Recomendación
Replicar en toggle_status la misma validación de rol que ya existe en el bloque de eliminación
if (isset($_GET['toggle_status'])) { $user_id = intval($_GET['toggle_status']); $stmt = $conn->prepare("SELECT rol, active FROM user WHERE user_id = ?"); $stmt->bind_param("i", $user_id); $stmt->execute(); $row = $stmt->get_result()->fetch_assoc(); if ($row['rol'] == 1) { $_SESSION['message'] = "No se puede modificar el estado de otro administrador"; $_SESSION['message_type'] = "error"; } elseif ($id != $user_id) { // ... continuar con la actualización usando prepared statements } }

Visión General del Sistema
Aspectos Positivos

BuildSafe System demuestra una base funcional sólida para la gestión de inventario. El sistema implementa correctamente el bloqueo de cuentas tras intentos fallidos de autenticación, lo cual es una medida de seguridad activa. El uso de password_hash() y password_verify() con bcrypt para la mayoría de los usuarios garantiza un almacenamiento seguro de contraseñas. La integración de Google reCAPTCHA v2 dificulta los ataques automatizados. El módulo de bitácora (binnacle) representa una buena práctica de auditoría interna.

Seguridad — Plan de Remediación Priorizado
  • Inmediato (24-48h): Revocar y regenerar la App Password de Gmail expuesta (HAL-003). Deshabilitar SMTPDebug (HAL-004). Eliminar test2.sql, generar_hash.php del webroot (HAL-010).
  • Corto plazo (1-2 semanas): Corregir SQL injection en add_user.php con prepared statements (HAL-006). Implementar CSRF en todos los formularios (HAL-008). Cambiar operaciones GET a POST en list_user.php, list_material.php y list_materials2.php — ambas interfaces de rol 1 y rol 2 (HAL-007). Migrar list_material.php a prepared statements igual que su par list_materials.php/list_materials2.php (HAL-009). Replicar en toggle_status la validación de rol que ya existe en el bloque de eliminación (HAL-016).
  • Mediano plazo (1 mes): Agregar session_regenerate_id() tras login (HAL-001). Migrar todas las consultas a prepared statements (HAL-009). Implementar rate limiting en recuperación (HAL-005).
  • Mantenimiento (próximo ciclo): Agregar cabeceras HTTP de seguridad (HAL-015). Mover credenciales a variables de entorno (HAL-003, HAL-014). Corregir error lógico en head.php (HAL-002). Documentar instalación, variables de entorno y roles del sistema (HAL-017).
Código Fuente y Arquitectura

Se recomienda adoptar un patrón de arquitectura MVC (Model-View-Controller) o al menos separar la lógica de negocio de la presentación. Los archivos actuales mezclan HTML, PHP y SQL en las mismas vistas, lo que dificulta la revisión de seguridad y el mantenimiento. Se sugiere crear un directorio includes/ para la capa de acceso a datos, utilizando exclusivamente prepared statements.

Control de Versiones y Documentación

Inicializar un repositorio Git con un .gitignore que excluya .env, backups SQL y archivos de configuración locales. Documentar el proceso de despliegue y las variables de entorno requeridas. Establecer un flujo de revisión de código (code review) antes de cualquier merge a producción.

Consideraciones Legales — Venezuela

Las vulnerabilidades críticas identificadas, en particular la exposición de contraseñas y datos de usuarios, pueden comprometer el cumplimiento de las disposiciones del Decreto con Fuerza de Ley sobre Mensajes de Datos y Firmas Electrónicas (2001) y la Ley Especial contra los Delitos Informáticos (2001) de Venezuela, que establece responsabilidades para los custodios de datos electrónicos. Se recomienda corrección inmediata previo a cualquier despliegue en ambiente de producción con datos reales.

Conclusiones Finales

La auditoría de seguridad realizada al sistema BuildSafe System de CONFALVI C.A. evidencia que el sistema posee una postura de seguridad deficiente que impide su despliegue responsable en un entorno de producción accesible públicamente en su estado actual. Los 27 hallazgos identificados (17 de la revisión estática del código fuente y 10 adicionales confirmados con OWASP ZAP y Lighthouse, sección 8) abarcan las capas de autenticación, manejo de datos, configuración del servidor, gestión de credenciales, control de acceso y dependencias de terceros.

Veredicto: No Apto para Producción

El sistema presenta 2 vulnerabilidades críticas activas que deben ser corregidas antes de cualquier despliegue. La exposición de credenciales SMTP y el dump de base de datos accesible vía HTTP representan riesgos inmediatos y explotables sin necesidad de conocimientos técnicos avanzados. Adicionalmente, se identificó un patrón de construcción de consultas SQL inseguro (HAL-006) que, si bien no resultó explotable en la versión de PHP actualmente instalada, debe corregirse por no constituir una defensa real.

Lo que funciona bien
  • Bloqueo de cuentas tras intentos fallidos
  • Hash bcrypt para la mayoría de contraseñas
  • reCAPTCHA v2 en el login
  • Bitácora de auditoría de acciones
  • Separación de roles admin/usuario
  • Transacciones en movimientos de inventario
Requiere corrección inmediata
  • Revocar App Password de Gmail expuesta
  • Deshabilitar SMTPDebug
  • Eliminar test2.sql del webroot
  • Migrar la consulta de duplicados de add_user.php a prepared statements (HAL-006)
  • Implementar protección CSRF
  • Cambiar acciones destructivas de GET a POST
  • Validar rol de administrador en toggle_status (HAL-016)

Una vez corregidos los hallazgos críticos y altos, se recomienda realizar una segunda auditoría de validación para confirmar la efectividad de los controles implementados. Con las correcciones aplicadas, BuildSafe System tiene el potencial de convertirse en un sistema robusto y seguro para la gestión de inventario de CONFALVI C.A.

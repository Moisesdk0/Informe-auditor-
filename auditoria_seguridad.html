Hallazgos — Severidad Crítica
Crítico C-01 Inyección SQL en verificación de duplicados de usuario add_user.php:29

La función htmlspecialchars() sin la bandera ENT_QUOTES no escapa comillas simples ('). Esto permite a un atacante inyectar SQL directamente en la consulta de verificación, pudiendo bypassear la lógica, extraer datos de la base de datos o modificar registros. Categoría OWASP: A03 — Injection.

// VULNERABLE: htmlspecialchars() no protege contra SQL Injection $email = htmlspecialchars($_POST['email']); // ' no escapa $user = htmlspecialchars($_POST['user']); $check_user = mysqli_query($conn, "SELECT * FROM user WHERE name = '$user' OR gmail = '$email'" ); // Payload malicioso: email = ' OR '1'='1
✓ Corrección Recomendada

Reemplazar con Prepared Statements que separan los datos del SQL:

$check_stmt = $conn->prepare("SELECT user_id FROM user WHERE name = ? OR gmail = ?"); $check_stmt->bind_param("ss", $user, $email); $check_stmt->execute(); $result = $check_stmt->get_result();
Crítico C-02 Credenciales de correo hardcodeadas en código fuente enviar_token.php:37-38

La contraseña de aplicación de Gmail está escrita directamente en el código fuente. Cualquier persona con acceso al servidor, al repositorio o a un backup puede obtener esta credencial y usarla para enviar correos masivos, spam o acceder a la cuenta. Categoría OWASP: A07 — Fallas de Identificación y Autenticación.

$mail->Username = 'uptag2026@gmail.com'; // ← Expuesto $mail->Password = 'xwnlhyllvdpdamyn'; // ← App Password Gmail expuesta
✓ Corrección Recomendada

Usar variables de entorno o un archivo .env fuera del webroot, nunca en el código:

$mail->Username = getenv('MAIL_USER'); $mail->Password = getenv('MAIL_PASS'); // En archivo .env (fuera de htdocs, NO subir a git) MAIL_USER=uptag2026@gmail.com MAIL_PASS=xwnlhyllvdpdamyn
Crítico C-03 Modo debug SMTP activo — vuelca sesión completa al navegador enviar_token.php:41

El nivel de debug 3 en PHPMailer imprime toda la comunicación SMTP en la respuesta HTTP, incluyendo el servidor, las credenciales negociadas y el contenido completo del correo. Esto expone información sensible a cualquier usuario que intente recuperar contraseña. Categoría OWASP: A09 — Fallas en el Registro y Monitoreo.

$mail->SMTPDebug = 3; // ← Imprime sesión SMTP completa al HTML // Salida visible al usuario: // "CLIENT -> SERVER: AUTH LOGIN" // "CLIENT -> SERVER: [credencial en base64]"
✓ Corrección Recomendada
$mail->SMTPDebug = 0; // Deshabilitar en producción // Usar logs del servidor para depuración, no salida HTML
6
Hallazgos — Severidad Alta
Alto A-01 Archivos sensibles accesibles públicamente en el webroot test2.sql / generar_hash.php

El dump completo de la base de datos (test2.sql) está accesible vía HTTP. Contiene hashes de contraseñas, tokens de recuperación, emails reales y toda la estructura de datos. Además, generar_hash.php es una utilidad que permite generar hashes arbitrarios. Categoría OWASP: A05 — Configuración de Seguridad Incorrecta.

// Accesibles públicamente: http://dominio.com/buildsafe_system1/test2.sql // Dump BD completo http://dominio.com/buildsafe_system1/generar_hash.php // Utilidad de hash http://dominio.com/buildsafe_system1/test.php // Archivo de pruebas
✓ Corrección Recomendada

Eliminar generar_hash.php y test.php. Mover test2.sql fuera del webroot o bloquearlo en Apache:

# En .htaccess <FilesMatch "\.(sql|log|env|bak)$"> Require all denied </FilesMatch>
Alto A-02 Sin protección CSRF en ningún formulario del sistema add_user.php, edit_user.php, register_movement.php

Ningún formulario implementa tokens CSRF. Un atacante puede crear una página externa que, al ser visitada por un administrador autenticado, ejecute acciones sin su conocimiento: crear usuarios, eliminar registros, cambiar estados de inventario. Categoría OWASP: A01 — Control de Acceso Roto.

✓ Corrección Recomendada
// En head.php — generar token if (empty($_SESSION['csrf_token'])) { $_SESSION['csrf_token'] = bin2hex(random_bytes(32)); } // En cada formulario HTML <input type="hidden" name="csrf_token" value="<?= $_SESSION['csrf_token'] ?>"> // Al procesar el POST — validar if ($_POST['csrf_token'] !== $_SESSION['csrf_token']) { die('Token CSRF inválido'); }
Alto A-03 Operaciones destructivas ejecutadas por petición GET list_user.php:5,46

Eliminar usuarios y cambiar su estado activo/inactivo se realiza mediante parámetros GET. Basta con que un admin autenticado visite un enlace malicioso para que la acción se ejecute. Los navegadores precargan enlaces, los motores de búsqueda los indexan y los logs los registran. Categoría OWASP: A01 — Control de Acceso Roto.

// Eliminar usuario con solo visitar la URL: GET /list_user.php?delete_id=3 GET /list_user.php?toggle_status=5
✓ Corrección Recomendada

Las operaciones de escritura deben ser siempre POST con token CSRF. Convertir los links a formularios con método POST.

Alto A-04 Consultas SQL mixtas sin prepared statements list_user.php:52,58,65

Varias consultas críticas mezclan mysqli_query() directo con variables interpoladas, en lugar de usar prepared statements. Aunque en estos casos los valores son enteros seguros, el patrón es peligroso y propenso a introducir vulnerabilidades en futuras modificaciones. Categoría OWASP: A03 — Injection.

// Patrón inseguro — consulta directa interpolada mysqli_query($conn, "UPDATE user SET active = $new_status WHERE user_id = $user_id" ); mysqli_query($conn, "INSERT INTO binnacle ... VALUES ('$time', $action, $id)" );

Hallazgos — Severidad Media
Medio M-01 Sin regeneración de sesión tras autenticación exitosa index.php:88-116

Al iniciar sesión correctamente no se llama session_regenerate_id(true). Esto permite ataques de session fixation: un atacante puede obtener un ID de sesión antes del login (por ejemplo desde una red compartida) y reutilizarlo con privilegios de administrador una vez que la víctima se autentica. Categoría OWASP: A07 — Fallas de Identificación.

✓ Corrección — agregar en index.php antes de asignar $_SESSION
// Justo después de verificar password_verify(): session_regenerate_id(true); // ← Genera nuevo ID de sesión $_SESSION['user'] = $result['name']; $_SESSION['id'] = $result['user_id']; // ... resto de variables de sesión
Medio M-02 Exposición de errores internos de base de datos al usuario add_user.php:56, list_user.php:35,71, edit_user.php:65

Los mensajes de error de MySQL se muestran directamente al usuario final. Esto revela la estructura de tablas, nombres de columnas y detalles del motor de base de datos que facilitan ataques de reconocimiento. Categoría OWASP: A05 — Configuración de Seguridad Incorrecta.

// Expone estructura interna de la BD: $message = "Error al crear el usuario: " . $conn->error; $_SESSION['message'] = "Error al eliminar: " . mysqli_error($conn);
✓ Corrección
// Mostrar mensaje genérico al usuario $message = "Error interno. Por favor contacte al administrador."; // Registrar el error real en el log del servidor error_log("DB Error: " . $conn->error);
Medio M-03 Contraseña en texto plano en la base de datos test2.sql — user_id=9

El usuario con user_id=9 (ds@gmail.com) tiene la contraseña 123456 almacenada sin ningún tipo de hash en la tabla user. Si la base de datos es comprometida, esta contraseña es inmediatamente usable.

✓ Corrección
-- En phpMyAdmin, actualizar con hash bcrypt: UPDATE user SET password = '$2y$10$[hash_generado_con_password_hash]' WHERE user_id = 9;
Medio M-04 Sin límite de peticiones en recuperación de contraseña enviar_token.php

El endpoint de recuperación de contraseña no implementa ningún tipo de rate limiting. Un atacante puede generar miles de correos hacia cualquier dirección registrada, usando el servidor de correo de la empresa como herramienta de spam. Categoría OWASP: A07 — Fallas de Identificación.

✓ Corrección
// Verificar que no haya token activo reciente (< 15 min) $stmt = $conn->prepare( "SELECT token_expiracion FROM user WHERE gmail = ? AND token_expiracion > NOW() - INTERVAL 15 MINUTE" ); $stmt->bind_param("s", $email); $stmt->execute(); if ($stmt->get_result()->num_rows > 0) { $_SESSION['error'] = "Ya enviamos un enlace recientemente. Espera 15 minutos."; header("Location: recuperar.php"); exit(); }
Medio M-05 Error lógico sutil en verificación de autorización head.php:12

La condición de autorización tiene un problema de precedencia de operadores. Aunque funciona correctamente en la práctica, es código engañoso que puede introducir fallos de seguridad si se modifica sin entender la evaluación correcta.

// Ambiguo: (!$seccion) == true ← no es lo mismo que !($seccion == true) if(!$seccion == true || $rol != 1) { ... }
✓ Corrección
if ($seccion !== true || $rol !== 1) { header("Location: destroyer.php"); exit(); }

$secretkey = "6LdVkrIrAAAAALXGfzMhYeIlaTLb1wDkX8NgHTVI";

$secretkey = getenv('RECAPTCHA_SECRET');
Bajo B-02 Sin cabeceras de seguridad HTTP head.php / index.php

El sistema no envía cabeceras de seguridad HTTP que mitiguen ataques de clickjacking, inyección de contenido y MIME-sniffing. Categoría OWASP: A05 — Configuración de Seguridad Incorrecta.

✓ Agregar en head.php o en .htaccess
header("X-Frame-Options: DENY"); header("X-Content-Type-Options: nosniff"); header("X-XSS-Protection: 1; mode=block"); header("Referrer-Policy: strict-origin-when-cross-origin"); header("Content-Security-Policy: default-src 'self' https://cdn.jsdelivr.net");

Conclusiones y Plan de Remediación

Evaluación General

El sistema BuildSafe System presenta 14 vulnerabilidades de seguridad, de las cuales 3 son de severidad crítica y requieren atención inmediata antes de cualquier despliegue en producción. El mayor riesgo proviene de las credenciales expuestas en el código fuente y la vulnerabilidad de inyección SQL, que combinadas podrían comprometer completamente el sistema y los datos de los usuarios.

  • Prioridad 1 (Esta semana): Eliminar credenciales hardcodeadas, deshabilitar SMTPDebug, mover archivos sensibles fuera del webroot, corregir SQL injection en add_user.php.
  • Prioridad 2 (Próximas 2 semanas): Implementar protección CSRF en todos los formularios, convertir operaciones GET a POST, agregar regeneración de sesión.
  • Prioridad 3 (Próximo mes): Implementar rate limiting, agregar cabeceras de seguridad HTTP, migrar todas las consultas a prepared statements, revisar y actualizar contraseñas en texto plano.
